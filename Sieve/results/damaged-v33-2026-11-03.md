# Damaged v33 files, W1 among them (3 November 2026)

The 600 damaged files tried before v33 was frozen came before mixing primed on MDN's examples
(`W1`). This run gives the readers damaged copies of `.sieve` files that use `W1` in every place it
can be, and the earlier review's samples of v33's other ways. Made with `tools/damage_test.py`.

## The samples

| Sample | Bytes | What it holds |
| :--- | ---: | :--- |
| one | 951 | a page (Pages/sieve.html) mixed alone, primed: `mix4 B16 F80 W1` |
| site | 19,422 | Edward's site's 11 pages mixed as one group, primed (`mixt ... W1`) |
| stream | 7,570 | a page cut into 299 files of 100 bytes: the lzma2 stream mixed, primed (`mix4 B16 F80 W1 R1 M4 C2`) |
| testsite | 450,470 | the web test site's sources: 5 files mixed primed, pictures by LZMA2 |
| mix33 | 113,028 | the v33 review's folder: copies, spans of binary written as text, a program mixed through the x86 filter, a palette picture, runs |
| small | 13,258 | the v33 review's small folder |

## The damage

Each copy had one of: a bit flipped, a byte changed, the file cut short, 2 to 8 bytes
overwritten, a byte inserted, a byte deleted, or one character of a mixing parameter changed
(`W1` to `W7`, `B16` to `B19`, `F80` to `F8x`, and so on). Half the damage fell in the first 400
bytes, where the head and the listing are.

## Results

| Reader | Damaged files | Refused | Installed the same | Different, crashed or hung |
| :--- | ---: | ---: | ---: | ---: |
| `sieve install` | 1,800 (300 a sample) | 1,772 | 28 | 0 |
| `sieve-install` | 600 (100 a sample) | 590 | 10 | 0 |
| the oracle (`sieve_ref.py unpack`) | 160 (one, site, stream, small) | 160 | 0 | 0 |
| `sieve install`, built with `-fsanitize=address,undefined` | 600 (100 a sample) | 593 | 7 | 0 (see below) |

"Installed the same" is damage that changed nothing a reader uses (a byte past the end it reads,
say): every file was checked against its SHA-256 and came out as the clean install. No reader
wrote a file that differed, ran out of time or crashed.

**The sanitizer build** reported 33 files of the `mix33` sample, all as one finding: a 32-bit read
and write at an address not a multiple of 4, in 7-Zip's x86 filter (`third_party/lzma/Bra86.c`,
lines 73 to 156). The undamaged `mix33.sieve` reports the same, so the damage did not cause it:
7-Zip reads instructions' addresses at any byte, on purpose, on processors that allow it
(`MY_CPU_LE_UNALIGN` in its `CpuArch.h`: x86, x64, ARM64), which are the ones Sieve is built for.
With that one check silenced for that file (`UBSAN_OPTIONS=suppressions=...`, `alignment:Bra86.c`),
the 33 gave no report: 31 refused, 2 installed the same. AddressSanitizer itself (reads and writes
outside memory, use after free) reported nothing in any of the 600.

## Found on the way: the web extension's host

Not from the damaged files: Edward's CI (step 11) stopped where the web extension's host lists the
test site's `directory.sieve`. Since `W1`, web text under 4 KiB is mixed too, with the word list,
and the host (`sieve web-host`, started by the browser) was never given the word lists or the
primers: it refused the folder's `index.html` ("carry a file mixed with a word list"). The host now
has what installing has (`use_item_maker` before `run_web_host`, tools/sieve_cli.cpp), and lists
and decodes it.
