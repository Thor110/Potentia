# The reader fuzzed again: the new recipes, and a guard in preflate (8 November 2026)

The reader's new parts (`tiff`, `pcx`, floats under `flac`, and `sk` reached by the zlib scan) were
fuzzed as on 6 November (results/fuzz-2026-11-06.md: `tools/fuzz/fuzz_reader.py`, a build with
AddressSanitizer and UndefinedBehaviorSanitizer, valid `.sieve` files changed and installed), the
fuzzer's list of ways given `tiff` and `pcx`.

| Round | Seeds (CI step 11's) | Runs | Found |
| :--- | :--- | ---: | ---: |
| 1 | TIFFs (t34), floats (fl34) | 8,680 | 0 |
| 2 | TIFFs, PCXs (x34), zlib streams (z34) | 7,964 | 6, one cause |
| 3 | the same, after the guard below | 5,501 | 0 |

**What round 2 found.** Every case was one crash: preflate, remaking a deflate stream from what an `sk`
skeleton carries, read outside its buffer (a SEGV in `PreflatePredictorState::prefixCompare`). The
cause: preflate's token predictor takes a corrected reference's length from the instructions without
checking it, and a damaged one gave 0; `firstMatch(0)` then compared from `0 - 1`, about 4 GiB past
the buffer. Its parameters (level, memory level, window) were valid in every case. This was in the
reader since v21 (zips, gzips), not in anything new; the zlib scan's seed is what reached it.

**Fixed** in Sieve's build of preflate (CMakeLists.txt, the second of two checked patches applied to
the fetched copy; configuring stops if preflate's text is not as expected): in its decoding alone, a
corrected length outside deflate's 3 to 258, a stored block longer than the bytes left, a token asked
for with no bytes left, and a reference longer than the bytes left or reaching before the start each
make the prediction fail, as a damaged stream's does; the install then refuses it ("preflate could not
make a deflate stream again"). Valid streams never ask for any of these: this repository's git pack
(2,737 streams) and two PDFs pack to the same bytes as before and install byte for byte; the unit
suite and CI step 11 pass.
