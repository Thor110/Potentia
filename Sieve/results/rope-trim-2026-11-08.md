# Trimming what the wave predicts exactly (8 November 2026)

Edward's idea (8 November 2026): run the wave through a file; every value it predicts exactly is
trimmed out, so the file shrinks; decoding runs the wave again in order and puts each trimmed value
back where it came from. Passes may repeat over what is left: a second wave over the kept values, or
noise from a seed run through them (as IDEAS §19.128), its matches trimmed too.

**What the decoder needs.** To put a trimmed value back, the decoder must know, at each place, whether
a value was trimmed there. So a trim is a yes/no for every value, then the leftovers that were not
trimmed. Its cost is the yes/nos plus the kept leftovers; it gains only where the yes/nos are cheaper
together than the zeros were among the leftovers, which happens when they cluster (a run of silence, a
black margin), so that each yes/no is coded given the ones before it.

**How.** `tools/bench/trim_passes.py`: each file's leftovers under a `P3` wave as 16-bit values (as in
results/rope-roundings-2026-11-08.md), cut into two byte planes. Every variant is costed by one
adaptive coder: each symbol at its count so far, plus one for every symbol, so no table is free (the
static estimates of order 2 earlier overstated; noise showed a false 7%). The yes/nos are coded given
the eight before them. The variants:
- **now (order 0)**: each plane with one table, as the rope codes a plane;
- **order 1**: each plane given the high byte before;
- **trim 1 pass**: the yes/nos, then the kept leftovers at order 0;
- **trim + order 1**: the same, the kept leftovers at order 1;
- **trim 2 passes**: the kept leftovers predicted again from the kept one before, exact ones trimmed again;
- **trim + noise pass**: the kept leftovers less noise from a seed (the best of up to 256 seeds, 8 bits
  for the seed), its matches trimmed;
- **T1** and **trim + T1**: each plane per band of busy-ness, as the rope's `T1` splits them; the
  trim's yes/nos also given the band.

**What it shows.**
- **One trim pays a little, and most where exact predictions cluster.** On `mr`, a third of the values
  are predicted exactly and they come in runs, so the yes/nos cost far less than the zeros did:
  16.64% off order 0. On the WAVs, 1 to 2% are exact and the gain is 0.47 to 1.36%.
- **The bands already take most of it.** Quiet neighbourhoods are where the wave is exact, and `T1`
  gives them their own tables; against `T1` the trim saves 0.31 to 0.69% on the WAVs and 4.36% on `mr`.
- **It adds to order 1**, as the two catch different things (where the zeros are; how a leftover
  follows the one before): trim + order 1 is 1.52 to 3.70% off on the WAVs, against 0.88 to 2.60% for
  order 1 alone.
- **A second pass loses** (5 to 7% more on the WAVs). The kept leftovers are next to each other only
  after trimming; in the file they are apart, so the one before says little about the next.
- **A noise pass loses heavily** (27 to 116% more). Noise matches a 16-bit value one time in 65,536, so
  almost nothing is trimmed, and taking noise away turns the kept leftovers, which cluster near zero,
  into noise themselves. IDEAS §19.128 found the same for bytes.
- **The control** gains nothing; order 1's +0.48% on noise is the cost of learning 256 tables.

**Is it new?** By what it costs, a trim is a yes/no per value before its leftover, and coders have
done that for a long time: in flat areas JPEG-LS's run mode codes a stretch of pixels equal to the
one before as its length, and the significance flags of H.264 and HEVC say which coefficients are
zero, each in its own context, before the rest are coded. The trim's gain comes from coding the
yes/nos in context, which is what those do.

**Verdict.** One trim, its yes/nos coded given the eight before and the band, would take 0.15 to 0.69%
off the rope on these WAVs and x-ray, and 4.36% on `mr`; a second pass or a noise pass loses. Worth
building, if at all, together with order 1 (IDEAS §19.131). Not built.
