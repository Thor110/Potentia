# Three items with no new format: large files that will not shrink, weighing ahead, one copy of each (7 November 2026)

Edward chose items 1 to 3 of the plan of the morning: Optimise Search on files that will not
shrink, archives' and spans' weighings on the threads (IDEAS 19.120 (c)), and what the pre-release
review left (19.120: a RAR's members, code written twice). Every timing here is from this machine (4
cores, 15 GiB), one run each; each "the same bytes" is a comparison of the `.sieve` files made.

## 1. Large files that will not shrink

### A fault in the evening's sampling, found first

The evening of 6 November, a file of 16 MiB or more whose three samples of 1 MiB each saved under
2% to LZMA2 was given its LZMA2 figure from the samples, not from a whole pass. A file that repeats
far apart is like that in every sample, though LZMA2 over the whole finds the repeats:

| 20 MB of random bytes, three times (60 MB) | Bytes |
| :--- | ---: |
| `xz -9e` | 20,006,996 |
| Sieve, the evening of 6 November | 60,001,033 |
| Sieve now | 20,006,995 |

Now the samples stand for the whole only where nothing repeats far apart (`long_repeats`: points
chosen by the bytes themselves, about one each 4 KiB, the 64 bytes after each hashed; where 1% of
them or more are met again, the whole pass is made as before). The pass over 52 MB takes about
50 ms.

### Optimise Search

Optimise Search turns Try every way on for every file over 16 MiB ("mixed only so"). On a file
LZMA2 cannot shrink, that bought the rope's full search and mixing the whole file, which the rising
bar then refused: of the FLAC's 428 s, 171 s went on the rope's search and 229 s on mixing whole,
for the same bytes as without Optimise Search (51,783,003, made in 11.6 s).

Mixing's lead over LZMA2 on such a file's three samples tells what it does whole. On the FLAC:

| | LZMA2 | Mixing | Mixing's lead |
| :--- | ---: | ---: | ---: |
| Start (1 MiB) | 1,040,386 | 1,038,144 | 0.21% |
| Middle (1 MiB) | 1,047,242 | 1,044,018 | 0.31% |
| End (1 MiB) | 1,031,400 | 1,024,893 | 0.62% |
| Together | | | 0.38% |
| The whole file | 51,931,174 | 51,707,916 | 0.43% |

The bar it would have to clear at 52 MB is 1.26%. Now, under Optimise Search, a file over 16 MiB
that LZMA2 cannot shrink (by its samples, and repeating nothing far apart) has its three samples
mixed (each its best of mixing's three trials); where mixing's lead over LZMA2 on them is under
half the bar, Try every way stays off for it, as without Optimise Search.

| With Optimise Search | Before | After |
| :--- | ---: | ---: |
| The FLAC, 51,997,326 bytes | 428.4 s, 51,783,003 bytes | 43.4 s, 51,783,003 bytes |
| samba | 3,277,403 bytes | 3,277,403 bytes |
| mozilla | 13,376,239 bytes | 13,376,239 bytes |
| enwik8 | 21,431,896 bytes | 21,431,896 bytes |

(samba, mozilla and enwik8 shrink, so the change does not reach them; they were packed again to be
sure. Of the FLAC's 43.4 s, about 29 s are the samples' mixing: nine mixings of 1 MiB.)

## 2. Archives' and spans' weighings, a batch ahead on the threads

The step that opens archives and decodes spans went file by file. What each file's weighing there
reads that is its own alone is now worked out on the threads a batch ahead of it (four files a
thread, at most 64 MiB of them, and at most 256 MiB of a PNG's pixels): LZMA2's estimate of the file,
a text's spans with their four figures, and a PNG's makers' results (stb's way, and its skeleton's
only where stb's gives nothing) with LZMA2's estimate of each. The loop still decides file by file
in order, so it chooses as before.

| With Optimise Search | The step, before | After | The whole, before | After | Bytes |
| :--- | ---: | ---: | ---: | ---: | :--- |
| Edward's `Pages/` (40 files, 3.5 MB; 3 texts with spans) | 1.58 s | 0.87 s | 12.2 s | 11.7 s | the same, 2,122,557 |

before.) An archive's own opening and weighing (a zip's, a 7z's) is still one at a time.

## 3. What the pre-release review left

- **A RAR's members held to the files the install wrote.** Each member must be a file or folder this
  install wrote, or the RAR is not made again and says which; their modes, set before rar runs as
  they must be, are put back where the RAR does not match. (Not tried with a hostile listing: there
  is no writer of one here. The CI's RAR block passes.)
- **One reader of Sieve's numbers** (`sieve/varint.hpp`), in their shortest form only, in eight
  places; sieve-weights-v1's own reader made as strict. Unit checks for each fault.
- **One copy of the vault's decoders**: not-written-v1's (`written_readings`), ascii85 the vault's
  own. The two had come to differ on text not UTF-8.
- **One reader of a Llama config's sizes** (`llama_shape`), every size bounded: the layout's copy had
  none, so a config.json claiming 10^18 layers was listed until the memory ran out.
- **Fuzzed again** (the reader under AddressSanitizer and UndefinedBehaviorSanitizer, three workers,
  about 16,000 cases from 141 seeds): two reports, both the kinds found on 6 November (an allocation
  over 2 GiB for a listing changed to claim a file of 4 GiB; preflate's decoder on a damaged
  deflate difference), nothing new.

## From encode.su: installers carried as their files

A person on encode.su packed Adobe Reader 9.4.0's setup and the CMZ corpus. Two faults showed:

- **An archive whose members every system cannot write was opened.** A cab in the setup held
  `turnonnotificationinactrobat.`, which Windows cannot hold, so the installer refused the whole
  install there. Now such an archive (a member name Windows cannot hold, two names one where case is
  ignored, or one in NFC and NFD) is left as it is, and the packer says why. Checked with two zips
  in CI step 11: left as they are, installed byte for byte (before, the first was carried as its
  contents).
- **Archives carried as their contents changed what was installed.** That is Archive and
  Compressed Formats: permanent, by design; on the command line `--optimise-archives` alone turned
  it on. Now (Edward: "command line should ask explicitly") it is on only with
  `--compressed-permanent`, and packing warns, naming each archive installed as its contents and
  each picture re-saved ("Add a warning when files are repacked"), on the command line and in the
  File Locator's box. The CI lines that meant both now say both; a cab is checked left as it is by
  default and warned of under `--compressed-permanent`.
