# Review 5: the whole codebase

Ten reviewers, one an area each, read the whole of Sieve on 21 November 2026, each finding then put to a sceptic told to refute it (default: refuted). 80 findings; 57 kept (confirmed or plausible, and worth their fix), 23 set aside. Nothing here is fixed yet. "Changes outputs" marks a fix that would change an address, a .sieve byte, a filter verdict or a saved file, so needs a new version or Edward's word.

Ideas from the same review are in [CLAUDE-IDEAS.md](CLAUDE-IDEAS.md).

## Kept

### Core arithmetic, automata and addressing

- **R5-ARITH-1** (medium bug; confirmed) `core/src/model.cpp:80`: CharModel::train can use gigabytes before it rejects the settings, and still uses far too much when the settings are valid.
  - What: train() counts every (context, next symbol) pair in a dense table: counts.resize(counts.size() + N) for every new context slot, so each slot costs N x 8 bytes (2 KB at base 256). Up to order+1 slots are made per stream position. That is O(stream x order x N x 8) bytes, almost all of it for contexts that min_count and the parent rule throw away later. The base^order key-room check is only made in finish(), after counting. So for settings finish() will refuse, pw[k] = N^k has already wrapped in uint64 (with base 256 and order 9 the keys collide) and the dense table has already been filled. Reachable from the CLI: `sieve train --alphabet <any stacked/bytes alphabet> --order 9` on the corpus.
  - Fix: Cheapest and enough: run finish()'s key-room check (2^60 / N^order >= 1) at the top of train(), before anything is counted. If memory matters too, keep the dense counting but replace the N-wide row per slot with an unordered_map<uint64_t, uint64_t> keyed by key*N+symbol (or a sorted vector per slot). The kept contexts and counts stay the same, so serialise() and the sha256 do not change. Level-by-level pruning is optional.
- **R5-ARITH-7** (low bug; confirmed) `core/src/filter.cpp:501`: g_tabling entries are never removed (g_merging's are).
  - What: merge_plugins erases its per-key mutex from g_merging once the merge is stored (line 466). shared_table creates g_tabling[merge_key] (line 501) and never erases it. Every distinct merge key leaves an entry for the life of the process: the line id plus every plugin's name and provenance, which can be hundreds of bytes, and a heap mutex. The hallway re-settles stacks each time ticks change and OPTIMISE FILTERS tries combinations, so a long session accumulates them. The growth is slow but unbounded, in a cache that is otherwise kept within merge_cache_share().
  - Fix: At the end of shared_table, under g_merged_mx, call g_tabling.erase(merge_key) after storing the table. Threads already waiting keep the mutex alive through their shared_ptr copy. In the same pruning loop, also erase outer g_tables_used entries whose inner map has become empty. Those keys leak in the same way: the loop removes the expired inner entries but never the outer key.
- **R5-ARITH-6** (low optimisation; confirmed) `core/src/filter.cpp:485`: shared_table matches kept tables by the length they were asked at, not the length their table covers.
  - What: find() considers each kept or used ranker by its map key `len`, the length it was requested at. A view made by DfaRanker(longer, length) holds the longer table's rows, and table_length() reports them. If the full-length ranker's weak_ptr has expired while a shorter view is still alive (pages at 32 alive, books at 128 gone), a request at a length between the two cannot use the view's 128-row table. It builds a new table: seconds and about 100 MB for the every-text-plugin merge. DfaRanker(const DfaRanker&, uint32_t) already accepts any length up to longer.table_length(), so a view of a view is valid.
  - Fix: In consider(), use t->table_length() for both the >= length test and the ordering (`!best || t->table_length() < best->table_length()`). Keep the `best->length() == length` shortcut for returning best directly.
- **R5-ARITH-3** (low performance; confirmed) `core/src/guided.cpp:163`: GuidedLine::interval copies and multiplies the width for every symbol where add_mul_small does it in place.
  - What: For each symbol, interval() runs `BigUint t = iv.width; t.mul_small(cum[s]); iv.low += t;`. That is an allocation, a full copy and two passes over a number that grows to S bits, so the copy is a large part of a loop that is already quadratic in the unit length. BigUint::add_mul_small(x, m) exists for exactly this shape (this += x*m, in place, no copy). Guided codes are worked out for every unit warped or shown in guided mode, and pages run to tens of thousands of characters. The same copy-then-mul_small-then-add pattern appears twice in count_filter (core/src/sieve.cpp:402-404 and 421-423).
  - Fix: Use `if (cum[s]) iv.low.add_mul_small(iv.width, cum[s]);` in guided.cpp. In sieve.cpp use `t.add_mul_small(F[p+k+1], w)` and `total.add_mul_small(F[k+1], m)`.

### Filters and plugins

- **F1** (high bug, changes outputs; confirmed) `core/src/plugin.cpp:1699`: Compiled-plugin cache key leaves out the word lists, so edited lists stay stale and the same .sfilter in two folders shares the first folder's words.
  - What: compiled_key() is built from the .sfilter's SHA-256, the symbols, the base and the parameter values only. A token plugin's `list:`/`tags:` files are read from PluginDef::folder, but neither the folder nor the lists' hashes are in the key. The memory cache (g_compiled) and the disk cache (sieve-dfa-cache-v1) therefore return an automaton built from whatever lists were there the first time. Two cases follow. (a) Edit words.txt beside a plugin and restart: the old automaton loads from disk, the judge keeps the old words, and the provenance's `w=list:w.txt=<sha>` still shows the old list's hash, because c->data is cached with it. (b) tools/cli/plugins.cpp reuses one parsed definition for identical bytes, and the in-process cache does the same: the same .sfilter in two folders with different lists gets the first folder's words. Counts, ranks and compact addresses then come from the wrong word set, and the provenance claims a list that is no longer on disk.
  - Fix: In compile_plugin_shared, before the key is built, hash every list:/tags: file of a token-form plugin (the same path rule the compiler uses) and append name=sha to the key. A missing file should make a key that can't hit the cache, so the compile reports the error as it does now. Also pass the bytes into TokenCompiler so each file is read once, and the hash in the data string always matches the words used. plugin_compiled() needs the same key, so it needs the PluginDef or the list hashes too.
- **F2** (medium bug; confirmed) `core/src/plugin.cpp:2054`: Token-form `within`: parameters not range-checked, choices and v2 constants missing, and a bad value fails as a bare "stoll".
  - What: Only the table form's Compiler checks integer values against min..max and turns choices into their index. TokenCompiler never looks at integer parameters, and plugin_within() evaluates `within` with plugin_env(). plugin_env() runs a raw std::stoll with no range check, skips choice parameters (its comment says they are included) and leaves out v2 constants such as BASE. Three results: `param n int 2 1 3` with n=99 is accepted and gives within=99; n=x fails with the message "stoll"; `within {mode + 2}` with a choice parameter fails with "'mode' is not a parameter".
  - Fix: Factor the Compiler constructor's env setup (v2 line constants, choices by index, integer parse with a clear 'must be a whole number between lo and hi' error) into one helper and use it in both Compiler and plugin_env. The range check only refuses values outside the declared min/max, which were never meant to be valid. Every in-range value gives the same `within`, so no address changes for valid settings.
- **F3** (medium bug; confirmed) `core/src/plugin.cpp:1274`: `list:`/`tags:` file names can leave the plugin's folder, and an untrusted .sfilter then shows the file's first line in its error.
  - What: read_list() and the `list` branch join `folder + "/" + name` with no check, so `list:../x` or `tags:../../x:N` reads any file the user can read. For `list:`, the first line that is not a word of the line's symbols is copied into the error message ("'<line>' is not a word of lower27's symbols"), which the menu and the designer display. Shared .sfilter files are untrusted input, and FILTER-PLUGINS.md says lists live beside the plugin.
  - Fix: Don't refuse every '/'. A user plugin may keep its lists in a subfolder. Refuse names that are absolute, have a drive letter or a leading '/' or '\', or contain a '..' path component, in the C++ parser and in the oracle. Optionally, quote the line number only, not the line's text, in the 'not a word' error.
- **F6** (medium optimisation; confirmed) `core/src/plugin.cpp:2128`: make_dfa_filter copies kept automata on every make (rows-alike 16x16: about 43 MB and 6 ms each time).
  - What: make_dfa_filter takes a Dfa by value and wraps a fresh shared_ptr around it. Callers that hold a process-kept automaton (picture.cpp specks, gradient and rows-alike via kept_dfa; written.cpp not-other-line and not-packed) pass `**d`, which copies next/accept on every stack build. The menu and hallway rebuild stacks often, and every live stack holds its own copy next to the kept one. PluginFilter already stores a shared_ptr<const Dfa> (compile_plugin_shared shares plugin automata for the same reason).
  - Fix: Add make_dfa_filter(std::shared_ptr<const Dfa>, uint32_t, std::string) and, at the five kept call sites, pass std::shared_ptr<const Dfa>(d, &**d), an aliasing pointer that keeps the kept optional alive. Leave the by-value overload for the callers that move in a fresh automaton.
- **F7** (low performance; confirmed) `core/src/filters/statistics.cpp:116`: symbol-entropy judges each unit through a std::map of counts (about 70 µs a page).
  - What: SymbolEntropy::passes builds a std::map<uint32_t,uint64_t> for every unit and copies it into a vector. The verdict depends only on the multiset of counts, so a vector<uint32_t> indexed by symbol (the base is at most 65536 on these lines, or a sort of the unit for very large bases) gives the same counts with no allocation per symbol. Every unit the hallway shows and every guided or judge walk calls it.
  - Fix: Do not keep a thread_local vector of size base_: base can be the whole of Unicode (about 1.1M), and clearing it every call would cost more than the map. Use a std::vector<uint32_t> counts(base_) on the stack only when base_ is at most about 4096 (or at most u.size()*4). Otherwise copy the unit, sort the copy and count the runs. Put the non-zero counts into the vector and call passes_counts as now.

### The lines' spaces and sieves

- **S1** (high bug; confirmed) `core/src/notes3.cpp:184`: canonicalise_notes3 caps the splits of each event but not their total: 88 bytes of notation take 1.2 GB.
  - What: kMostSplits (2^24) is checked once per event, but every event is then expanded into `ticks / longest` digits with no bound on the sum. On a set whose longest length is 1 (make_notes3_set allows longest=1), each 10-byte token "R:16000000" adds 16M digits, which are packed into one std::vector per unit. The input is reachable from `sieve warp --line audio` on a notes3 line (tools/cli/lines.cpp:353), from the hallway's file opening (client/item_save.cpp, which goes through read_warp_input), and from MIDI read back through midi_to_notes3. The input can be pasted text or a MIDI file.
  - Fix: Keep one running count of digits across all voices (or per voice), checked before each push, and refuse past one bound (kMostSplits, 2^24, already exists) with the same kind of message. Checking (left+longest-1)/longest against what is left of the budget, before the while loop, stops it before any memory is spent.
- **S2** (high bug; confirmed) `core/src/audio.cpp:584`: midi_to_notation (notes2) writes out each grid step of a long delta: a 44-byte MIDI file becomes 403 MB of notation.
  - What: The SMF reader accepts any 4-byte delta (up to 2^28-1 ticks). With division=1 the shortest grid is one sixteenth, so steps(ticks) is about 4 x ticks. write() then emits one token per longest duration ("Rw " or a note) for every step, with no bound on the total. The resulting text goes to canonicalise_notes2, which creates one digit per token. This runs from `sieve warp/bind --file x.mid` on any notes2 line (tools/cli/lines.cpp:374), from the hallway's item opening (client/item_save.cpp:707) and from filter_config.cpp:589.
  - Fix: Before write(), check the grid steps per voice (e or cur+n) against a bound, for example 2^24 steps or the steps that 2^24 longest tokens hold (canonicalise_notes2 makes one digit per token anyway), and throw with the length in quarters. Also check that the summed end time does not wrap. The check belongs in midi_to_notation itself, so every caller is covered.
- **S3** (high bug; confirmed) `core/src/sound.cpp:161`: PcmCanoniser upsamples without a bound: a 2 KB WAV declaring 1 Hz becomes 96 million samples (725 MB).
  - What: read_wav accepts any non-zero rate. PcmCanoniser computes num_/den_ from gcd(source, target), and each source frame then yields target/source output samples. A tiny WAV whose header says 1 sample a second, warped onto pcm/48000, makes 48,000 samples per byte, all held in out_ and then copied into one vector per unit. This is reachable from `sieve warp --file` (tools/cli/lines.cpp:321) and from opening an item in the hallway on a pcm audio line (client/item_save.cpp:677). Both use read_media_audio, so ffmpeg-decoded formats with odd rates reach it too.
  - Fix: Bound the upsampling ratio in the constructor, not the total output, so long real recordings at ordinary rates are never refused: for example refuse when f.rate / source_rate > 64 (8 kHz to 192 kHz is 24). A minimum source rate of about 1,000 Hz also works. An absolute cap on out_[0].size() alone could refuse legitimate long recordings.
- **S4** (medium bug; confirmed) `core/src/aispace.cpp:51`: Building the AI line takes about 8 bytes of memory per weight; the shapes the setup menu allows run to tens of GB.
  - What: AiSpace's constructor builds size_ = 2^bits as a BigUint. It also copies it to top and writes the whole number out with top.to_hex() just to measure its width (2 hex chars a byte, as a std::string). Shuffle(size_) copies it again and stores n_hex_ (another full hex string), plus a transient msg copy. AiShape::check and the menu (client/menu.cpp:1625-1635) allow 64 layers x width 4096 x 8 bits, about 1.7e10 weights and 1.4e11 bits. That shape cannot be built: the hallway or menu runs out of memory as soon as the shape is chosen (Menu::ai_space(), hallway.cpp:152). A hostile manifest naming the shape gets the same result through tools/cli/items.cpp.
  - Fix: In stack_info, give the AI line the same check as the other lines: if ai_weights()*bits is over too_large_bits(), return 'too large' before calling ai_space(). The same guard belongs wherever ai_space() or AiSpace is built from settings. Set hex_width_ = max(1, (bits()+3)/4), which drops the transient to_hex copy and leaves output identical. A hard cap in AiShape::check is less safe than the memory-based guard, because the BigUint alone takes about 1 byte per weight; if one is added anyway, make it generous.
- **S7** (medium deduplication; confirmed) `core/src/audio.cpp:456`: Two copies of the Standard MIDI File reader (notes2 and notes3), and of the voice-split and unit-packing code.
  - What: midi_to_notation (audio.cpp:456-560) and midi_to_notes3 (notes3.cpp:388-504) repeat the same reader nearly line for line: MThd check, u32/u16 lambdas, the SMPTE refusal, the track loop, VLQ, meta and sysex skipping, running status, note-on/off pairing through a map, notes left open closed at the track's end, stable_sort by start. They differ only in whether velocity is kept. canonicalise_notes2 (audio.cpp:273-374) and canonicalise_notes3 (notes3.cpp:166-301) also share the "//" voice split, the token scan and the same unit packing loop (runs, padding). A fix to one reader (for example the bounds in S2) has to be made twice today.
  - Fix: Factor out only the byte-level reader: `struct MidiNote{uint64_t start,end; uint32_t pitch,velocity;}; struct MidiRead{uint32_t division; std::vector<std::vector<MidiNote>> voices; std::vector<uint64_t> ends;}; MidiRead read_midi(const std::vector<uint8_t>&)` in audio.cpp (declared in an internal header). Both callers keep their own grid and rounding. Make the S2 bounds fix once, inside it. Leave canonicalise_notes2/3 alone unless a bug needs both changed.
- **S6** (low bug, changes outputs; confirmed) `core/src/modelspace.cpp:313`: .obj face indices past 2^32 wrap on Linux and are skipped on Windows: the same file gives different meshes.
  - What: read_any_obj parses indices with std::stol into a long and then casts to uint32_t. On Linux/macOS (64-bit long), 4294967297 becomes vertex 0 and 99999999999 becomes 1215752190, so a bad index silently names a real vertex, and fit() counts it as clamped only by chance. On MSVC (32-bit long), stol throws out_of_range, the token is skipped, and the face loses a corner. The imported model, and so its address, depends on the platform. Callers are importers.cpp:951 (an .obj import) and character.cpp:369.
  - Fix: Parse with std::from_chars into int64_t (include <charconv>). On overflow or a value over UINT32_MAX, use UINT32_MAX (and for negatives past the start, skip as now), so fit() clamps the index and counts it in indices_clamped on every platform. Bump the obj importer's version and add a vector with an index past 2^32.

### Characters, saves, RAID, AI and the rest of core

- **gltf-sparse-overflow** (high bug; confirmed) `core/src/importers.cpp:293`: glTF sparse accessor writes past the end of the heap: count*comps overflows, but the sparse index is checked against count.
  - What: In Gltf::floats, `std::vector<float> out(size_t(count) * comps)` is allocated from the file's accessor count with no overflow check, and the `count > 2^32` roof in view_of only runs when the accessor has a bufferView. An accessor with no bufferView, a sparse block and count = 6148914691236517206 (0x5555555555555556) makes count*3 wrap to 2, so `out` holds 2 floats. The sparse check `if (at >= count)` compares against the unwrapped count, so a sparse index of 100000 passes, and read_into writes 3 floats at out.data()+300000. That is a heap write controlled by the file. The path is read_model -> read_gltf_json -> add_mesh -> floats, which the hallway viewer (client/viewer.cpp:812), item_save, the personal world, the character creator and `sieve` (tools/sieve_cli.cpp:1129/2027) all reach by opening a .gltf or .glb. Related: indices() allocates `std::vector<uint32_t>(count)` before any roof, and floats() allocates before view_of checks the count, so a count near 2^32 asks for 16 to 256 GB.
  - Fix: Put one guard at the top of floats() and indices(), before anything is allocated, that runs whether or not there is a bufferView: refuse count > 2^32 (or a roof tied to kMaxTriangles) and refuse count*comps > SIZE_MAX/sizeof(float). With both guards in place `at >= count` is safe again, but checking `at >= out.size()/comps` as well costs nothing.
- **gltf-amplification** (medium bug; confirmed) `core/src/importers.cpp:687`: glTF import has no roof on animations x nodes or on instanced vertices: a 122 KB file takes 18 s and 1.4 GB.
  - What: read_skeleton samples every animation for up to kAnimationMaxFrames (300) frames. Each frame copies the Rest of every node and works out world matrices for every node (world_matrices over nodes.size()), although only the at most 64 kept joints and their ancestors are read. Each animation also keeps 300*64 turns and places. The number of animations is unbounded, so memory and time grow as animations*frames*(nodes+64) from a small JSON. Separately, walk() calls add_mesh for each node that names a mesh. kMaxTriangles caps faces, but vertices are capped only at UINT32_MAX, so many nodes instancing one large POSITION accessor with an empty index list multiply the vertex count.
  - Fix: The roof is the essential part: cap the total sampled frames*kept bones across all animations (for example 1<<22) and cap total vertices in add_mesh, refusing with a reason. The ancestor-only matrix work is optional speed and should keep the per-joint multiplication order so the turns are bit-identical.
- **jpeg-eighth-scan-bomb** (medium bug; confirmed) `core/src/jpeg_dc.cpp:372`: jpeg_eighth decodes every SOS over the whole block grid even when its data is empty: a 357-byte JPEG takes 15 s and 0.5 GB.
  - What: Once a scan's entropy-coded data runs out, Bits feeds zeros. If the Huffman tables give the all-zeros code a value (one 1-bit DC code and one 1-bit AC EOB), every block decodes successfully from nothing. The frame may be 65535x65535: the 1 GiB guard allows about 67M blocks, 0.5 GB of dc, and that memory is taken as soon as the SOF is read. The number of SOS segments is not limited, so each extra 10-byte SOS adds another pass over all 67M blocks. The viewer's reduced path for large pictures (client/picture_source.cpp:208) calls jpeg_eighth on files the user opens.
  - Fix: The simplest fix is to return nullopt when a non-refinement scan's coded bytes (data_end - data_start) are fewer than blocks*2/8. That covers the empty-scan case with one comparison and needs no change to Bits. Refinement scans, at one bit per block, can be bounded the same way with blocks/8.
- **cipher-hex-key-dup** (low deduplication; confirmed) `core/src/cipher.cpp:35`: parse_layer repeats the hex-key reader for xor and for vigenere-hex/feistel-hex.
  - What: The `xor` branch (lines 35-45) and the `vigenere-hex`/`feistel-hex` branch (46-56) carry the same odd-length check and the same pair-of-hex-digits loop. Their error texts are equal when `word` is "xor": "xor needs a key of whole bytes in hex, not ..." and "xor needs a key in hex, not ...". Layer::text also has its own kHex table where hex.hpp's hex_of would do.
  - Fix: Inside the anonymous namespace, add `std::vector<uint8_t> hex_key(const std::string& word, const std::string& arg)` that runs the empty/odd check and the pair loop and builds its errors from `word`. Then merge the branches into `else if (word == "xor" || word == "vigenere-hex" || word == "feistel-hex") { l.key = hex_key(word, arg); l.kind = word == "xor" ? Xor : word == "vigenere-hex" ? Vigenere : Feistel; }`, keeping the key check before the kind is set as it is now. In Layer::text, use `const std::string h = hex_of(key);` and drop kHex.
- **weights-unpack-memory** (low performance; confirmed) `core/src/weights.cpp:263`: sieve-weights unpack holds each tensor twice in memory, and a one-symbol table decodes any element count from 2 words.
  - What: unpack decodes a tensor's whole value vector with weights::decode(words, table, t->elements()), then copies it into a second byte vector before emit. A 151936x896 BF16 embedding therefore takes 272 MB plus 272 MB beside the output. decode() runs n = t->elements() times, and n comes from the header. With a table of one symbol at frequency 2^24, x stays exactly kL and no words are read, so a header that claims 2^36 elements makes a 200-byte file try to build 128 GB in memory before anything is written. The comment above the stream read says the sizes are not trusted, but this path trusts them.
  - Fix: Add a callback form, decode(words, freq, n, sink) that hands over chunks of about 1<<20 values. unpack converts each chunk to little-endian bytes and passes it straight to emit. The vector form can stay as a thin wrapper over it for rope_wave.

### The packer and format codecs

- **R5-P1** (high bug, changes outputs; confirmed) `tools/cli/vault.cpp:265`: Vault's picture check fails open, and a GIF of a few KB can make it allocate many GB.
  - What: withheld_as_picture() checks one frame's size only (image_info, at most 8192x8192), then decode_image_frames() (image_io.cpp:52-75) calls stbi_load_gif_from_memory. That call builds every frame at full canvas size in one buffer, and then each frame is copied into its own vector, so memory is about 2 x frames x canvas x 4. A GIF frame can be a 1x1 sub-image that costs about 25 bytes, so a small file asks for any amount of memory. When the decode then throws (stb out of memory), the catch at vault.cpp:280-283 returns false, so the bytes count as clear. A vault-listed picture put in frame 1, followed by a few hundred 1-pixel frames, passes the PDQ check. The check runs on install (locate.cpp:3432 check_known), Extract (pack.cpp:7928 check_bytes), packing (hash_checked_file -> check_picture_file) and the web host (web_host.cpp:211). So a hostile .sieve or folder can also exhaust the machine's memory.
  - Fix: Keep stb (do not decode GIFs one frame at a time with new code). Before calling it, count the frames with the existing GIF block walker (gif_lzw.cpp) and refuse when frames x canvas x 4 (x2 for the copies) is over a budget. When the bytes are a picture and the budget or the decode fails, throw or withhold (fail closed), as v.st.failed_closed already does. Leave truly corrupt headers as they are, or also fail closed. Also move the frames out of stb's buffer instead of copying them, which halves the peak.
- **R5-P2** (high performance; confirmed) `tools/cli/text_spans.cpp:280`: spans_of is quadratic on lists of numbers whose separators vary: 36 s for 200 KB.
  - What: list_at() first collects every value up to where the list stops being values (lines 280-290). Only afterwards does it find where the separator/line-break pattern breaks (lines 296-310) and cut count back. When the pattern breaks early (for example a CSV mixing ', ' and ','), count is below 48 and list_at returns nothing. spans_of then moves p one byte and calls list_at again at the next word start, which collects the whole rest of the list again, for each of 4 prefixes x 3 forms. With spans on (the default v33+ path, weigh_spans in pack.cpp:4405), every text file of 256 bytes or more goes through this. Time grows with the square of the list's length.
  - Fix: As proposed: run the separator/per/line check inside the collecting loop and break at the first mismatch (count = k+1). Leave everything after that untouched. Add a test that compares the old and new spans_of output on random CSVs with mixed separators.
- **R5-P3** (medium performance; confirmed) `tools/cli/pack.cpp:2825`: gzip_recipe runs up to 18 full deflates with no early stop: about 0.75 s per MB for a gzip zlib did not make.
  - What: For every single-member gzip under Optimise archives, gzip_recipe deflates the whole content at 9 levels x 2 memory levels and compares only at the end. A gzip made by 7-Zip, libdeflate, zopfli, pigz or another encoder never matches, so all 18 run in full before preflate is tried. zstd_recipe and lz4_recipe test a prefix first, and brotli_recipe stops at the first differing byte (brotli_pack's `against`); gzip has nothing like that.
  - Fix: The smallest safe change is a prefix test like zstd_recipe's: deflate the first ~128-256 KiB of the input, check that the output is a prefix of the stream, and only then deflate in full. Note that a truncated input's output is not a true prefix at the point of truncation, so compare only up to output length minus a margin, or use streaming deflate with a small avail_out and compare as the output is made. Check against the zlib build actually linked (zlib vs zlib-ng) that the output is identical.
- **R5-B2** (low bug; confirmed) `tools/cli/pack.cpp:1400`: A skeleton's run of chunks (kind 5) allocates up to 128 MiB before reading what it claims.
  - What: deflate_skeleton_remake (install path, on bytes from the .sieve) accepts n up to 2^24 chunk lengths and makes std::vector<uint64_t>(n) at once, zero-filled, before reading any length. Each length needs at least one skeleton byte, so a few bytes of skeleton cost 128 MiB and the time to fill it before the read is refused.
